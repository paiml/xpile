## Premise

`crates/decy-frontend/` at v0.1.0 is a 35-line stub that matches
`.c` / `.h` extensions and returns an error. The standalone
`paiml/decy` repo at `/home/noah/src/decy` is **16 sub-crates**
including `decy-parser` (13 source files, real C parser) and
`decy-core`, `decy-codegen`, `decy-ownership`, `decy-analyzer`,
`decy-verify`. It is a working C → Rust transpiler that has been
maintained alongside depyler.

v0.2.0 brings decy's parser + lowering into xpile the same way
bashrs and (per Track 1) depyler are merged.

## Scope

### In scope for v0.2.0

| Standalone | xpile target | What it brings |
|---|---|---|
| `decy-parser` | extends `crates/decy-frontend/` | Real C parser (tree-sitter-c + ast extraction) |
| `decy-core::ast_types` | folded into `xpile-meta-hir` | C type representations: `int`, `unsigned`, pointers (later) |
| `decy-codegen` | extends `crates/xpile-rust-codegen/` | C → Rust lowering rules |
| `decy-ownership` (minimal subset) | new crate `crates/decy-analysis/` | Pointer-aliasing / lifetime analysis (stretch — owned-by-value first pass is sufficient for v0.2.0 exit) |

### Out of scope for v0.2.0 (deferred to v0.3+)

- Full pointer semantics (xpile starts with **stack/value-only C** —
  `int foo(int a, int b)`, no `*p`, no `malloc`)
- `decy-debugger`, `decy-repo`, `decy-stdlib`, `decy-book` —
  operational tooling; xpile has analogues
- `decy-llm`, `decy-mcp`, `decy-agent` — xpile has its own

The minimum-viable scope for v0.2.0: **C int/bool/control-flow
subset that mirrors what Python had at v0.1.0**, with the addition
that C arithmetic semantics differ from Python's.

## The substrate work: C-C-INT-ARITH

The single net-new substrate item: a new Layer-1 contract distinct
from `C-PY-INT-ARITH`. The shapes:

| | Python | C |
|---|---|---|
| `int` width | unbounded | implementation-defined fixed (typically `int32_t` for `int`) |
| Signed overflow | impossible (auto-promote to bigint) | **undefined behavior** — UB, not wraparound |
| `/` | floor division (`-7 // 2 == -4`) | truncating toward zero (`-7 / 2 == -3`) |
| `%` | floor remainder | sign-of-dividend remainder |

`contracts/c-int-arith-v1.yaml` (proposed) captures C's:

- "`int` is platform fixed-width signed; emit Rust `i32` by
  default, with a `target-platform`-overrideable width"
- "Signed-overflow paths emit `.checked_*().expect(\"…C-C-INT-ARITH
  undefined-behavior path…\")` — same shape as Python's bigint slow
  path, except *the slow path is UB, not a slow path*"
- "`/` and `%` lower to `i32::wrapping_div` / `wrapping_rem`
  (C-style truncation), NOT `checked_div_euclid` (Python-floor)"

Same 4-stratum quorum + Diamond ratchet as any Layer-1 contract.

## Sequencing

Three sub-tracks, mostly parallel with Track 1:

### 2.A `decy-frontend` real parser (~1 week)

1. Vendor `tree-sitter-c` (already a dep in standalone decy).
2. Port `decy-parser::extract::expressions` and `extract::statements`
   into `crates/decy-frontend/src/`. Modular: each AST extractor
   maps a tree-sitter node class to a meta-HIR variant.
3. The receiving meta-HIR variants are **the same ones Track 1
   adds for Python** — `Type::Int`, `Type::Bool`, control flow,
   recursion. No new variants needed for the int/bool subset.

### 2.B `C-C-INT-ARITH` substrate (~1 week)

1. Author `contracts/c-int-arith-v1.yaml`.
2. Write Lean theorems in `contracts/lean/CIntArith.lean` (Bronze
   tier first, then Silver/Gold/Platinum/Diamond — the substrate
   ratchet).
3. Write Kani harnesses in `contracts/kani/c_int_arith.rs`.
4. Wire `xpile quorum` → 13 QUORUM (was 12).
5. Wire `xpile diamond` to recognize the new contract; broaden the
   diamond-coverage CI gate to expect 13 contracts at depth-1
   (was 12).

### 2.C `xpile-rust-codegen` C path (~1 week)

1. The Rust backend already handles control flow + arithmetic
   for Python. For C, the new behaviour is:
   - Emit `i32` (not `i64`) by default for `int`
   - Emit `.wrapping_*()` (not `.checked_*().expect(...)`) for
     arithmetic, because C truncates rather than floors
   - Skip Python-floor in `/` and `%` lowering paths
2. Citation on every emitted function *whose body does C integer
   arithmetic*: `// xpile-contract: C-C-INT-ARITH` (not
   C-PY-INT-ARITH). Emit one line per ID returned by
   `applicable_contracts()`, none when it is empty — citing a
   comparison-only function is the `over_citations` bug `xpile audit`
   counts, not compliance (PMAT-1445; through v0.1.617 this step said
   "every emitted function" flat).
3. The `BackendConfig` gets a `source_lang: SourceLang` field
   threaded from the frontend — `xpile_meta_hir::SourceLang::C`
   selects the C-arith path.

## Exit criterion

```c
// add.c
int add(int a, int b) { return a + b; }

int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}
```

```bash
$ xpile transpile add.c
// xpile-generated from C module add

// xpile-contract: C-C-INT-ARITH
pub fn add(a: i32, b: i32) -> i32 { (a).wrapping_add(b) }

// xpile-contract: C-C-INT-ARITH
pub fn factorial(n: i32) -> i32 {
    if (n <= 1i32) { 1i32 } else { (n).wrapping_mul(factorial((n).wrapping_sub(1i32))) }
}
```

Note: **`wrapping_*`, not `checked_*`** — that's the entire point of
`C-C-INT-ARITH` vs `C-PY-INT-ARITH`. Different host language, same
contract substrate, different discharge strategy.

`xpile quorum` reports 13 contracts at QUORUM (was 12).
`xpile diamond` reports `C-C-INT-ARITH` joining the
12-contract-UNIVERSAL bandwagon — initially at depth-1, ratcheting
through 2..13 in subsequent broadening waves (re-using Templates
1-13 from the existing Diamond program).

## Risk register

| Risk | Mitigation |
|---|---|
| C's pointer/aliasing semantics drag the merger into a 3-month spec project | **Hard scope cut: no pointers in v0.2.0.** Stack-only `int add(int, int)` shape. Stub pointer args with an error pointing at v0.3.0. |
| C UB semantics are notoriously ambiguous (signed overflow, type punning, etc.) | The new contract `C-C-INT-ARITH` explicitly documents that signed overflow is UB and the emit path is `wrapping_*`, which preserves C's bit pattern without invoking Rust UB. This is the conservative, sound discharge. |
| `tree-sitter-c` is a heavy dep | bashrs already proved tree-sitter is a workable workspace dep at the v0.1.0 cadence. Same vendoring approach. |
| The Diamond program now has to broaden 13 contracts (was 12) every depth | One more contract per broadening sweep is ~1 PR of marginal cost. Acceptable. |

## What this is NOT

- **Not** a full C compiler. xpile compiles a substrate-constrained
  subset of C: stack variables, control flow, function calls,
  arithmetic. Pointers, allocations, strings, structs, unions, and
  `goto` are all v0.3.0+.
- **Not** a replacement for `cc`/`clang`. xpile produces Rust from C,
  not machine code from C. The Rust output is then compiled by the
  Rust toolchain.
- **Not** UB-preserving in the strict sense. Where C says "signed
  overflow is UB," xpile emits `wrapping_*` — which produces a
  deterministic result rather than UB. This is a *sound, more
  conservative* discharge of the contract; not a faithful UB
  reproduction.
