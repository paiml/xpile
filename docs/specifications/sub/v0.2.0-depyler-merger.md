## Premise

`crates/depyler-frontend/` at v0.1.0 is a 1,586-line single-file
extract that handles only the `int`/`bool` subset of Python. The
standalone `paiml/depyler` repo at `/home/noah/src/depyler` is **18
sub-crates, 310+ source files**, and has been the load-bearing
Python→Rust transpiler in the paiml fleet for over a year. It
already implements:

- `str` (owned + borrowed; lifetime inference)
- `list[T]`, `dict[K, V]`, `tuple[...]`, `set[T]`
- `float`, `bytes`, `bytearray`
- Borrowing analysis (`depyler-analysis`, `depyler-core::borrowing`)
- Ownership inference (the path to `&str` over forced-`String`)
- Annotation-aware type mapping
- Mutation analysis
- Quality scaffolding (`depyler-verify`, `depyler-quality`)

v0.2.0's load-bearing premise: **the Python type system is already
solved in standalone depyler; xpile just needs to absorb it**, the
same way `bashrs-frontend` + `bashrs-backend` absorbed the
standalone bashrs work.

## Scope

### In scope for v0.2.0

Bring the following standalone-depyler crates into the xpile
workspace, mirroring the bashrs-merger crate layout:

| Standalone | xpile target | What it brings |
|---|---|---|
| `depyler-hir`  | folded into `xpile-meta-hir` | `Type::Str`, `Type::List`, `Type::Dict`, `Type::Float`, etc. — new meta-HIR variants |
| `depyler-core::ast_bridge` | extends `crates/depyler-frontend/` | Python parsing for collections + strings + f-strings |
| `depyler-core::rust_gen` | extends `crates/xpile-rust-codegen/` | Lowering rules for `String`/`Vec<T>`/`HashMap` paths |
| `depyler-analysis` | new crate `crates/depyler-analysis/` (xpile-folded) | Borrowing / ownership / mutation analysis (the path to `&str` vs `String`) |
| `depyler-annotations` | folded into `xpile-meta-hir` | Annotation-aware type metadata |

### Out of scope for v0.2.0 (deferred to v0.3+)

- `depyler-agent`, `depyler-mcp` — xpile has its own agent + MCP crates
- `depyler-oracle` — superseded by `xpile-oracle`
- `depyler-verify`, `depyler-quality`, `depyler-knowledge` — xpile uses
  pmat + provable-contracts for these
- `depyler-corpus`, `depyler-testing`, `depyler-tooling` — xpile has its
  own fixture corpus + CI
- `depyler-lambda` — AWS Lambda deployment is out of xpile scope
- `depyler-ruchy` — xpile already has `xpile-ruchy-codegen`
- `depyler-graph` — visualization, not load-bearing

The merger is **type-system + parser + emit only**; the surrounding
operational tooling stays in standalone depyler or in xpile's
existing equivalents.

## Sequencing

Three sequential sub-tracks within Track 1:

### 1.A `str` (~2 weeks)

1. `xpile-meta-hir`: add `Type::Str`, `Expr::StrLit`, `Expr::Concat`,
   `Expr::FString { parts }`, `Expr::StrIndex`.
2. `depyler-frontend`: port `depyler-core::ast_bridge` paths for
   string literals, `str` annotations, `f"…"` formatting.
3. `xpile-rust-codegen`: port `depyler-core::rust_gen::expr_gen`
   string-emit paths. **First pass: owned `String` only** (no
   lifetime inference). `&str` work is in 1.D.
4. `xpile-lean-codegen`: lower to Lean `String`.
5. New contract `contracts/xlate-py-str-to-rust-string-v1.yaml` —
   Layer 2, code lane, kind: kernel. Alias / owned-by-default
   semantics, mirrors `xlate-py-list-to-vec-v1.yaml`.
6. Lean theorems + Kani harnesses for the new contract → QUORUM.
7. Diamond theorems: structure-extensionality, length-Nat-structure
   (Template 6 already exists for `String.length`).
8. Fixtures: `greeting.py`, `name_parser.py`.

### 1.B `list[T]` (~2 weeks)

1. `xpile-meta-hir`: parameterise `Expr::ListLit<T>`, add
   `Expr::Index`, `Stmt::ListAppend`, `Stmt::ForEach { iter, body }`.
2. `depyler-frontend`: port `depyler-core::ast_bridge` list paths;
   lower `for x in xs:` (non-range iteration — closes one ⏳
   item from spec §23).
3. `xpile-rust-codegen`: port list paths from
   `depyler-core::rust_gen`; emit `Vec<T>` + `.push()` + `[i]`.
4. `xpile-lean-codegen`: lower to Lean `List T`.
5. **`xlate-py-list-to-vec-v1.yaml` already exists at v0.1.0** —
   this sub-track adds equations + Diamond theorems for the new
   constructs.
6. Fixtures: `sum_list.py`, `max_list.py`, `filter_evens.py`.

### 1.C `dict[str, T]` (~1 week; depends on 1.A for keys)

1. `xpile-meta-hir`: `Type::Dict`, `Expr::DictLit`, `Expr::DictGet`,
   `Stmt::DictSet`.
2. `depyler-frontend`: port dict paths.
3. `xpile-rust-codegen`: lower to `HashMap<String, T>`.
4. `xpile-lean-codegen`: first pass `List (String × T)`, upgrade to
   `Std.HashMap` once Lean ergonomics warrant.
5. New contract `contracts/xlate-py-dict-to-hashmap-v1.yaml` — Layer 2,
   code lane, kind: kernel. Insertion-order / key-equality semantics.
6. Lean theorems + Kani harnesses → QUORUM.
7. Fixtures: `histogram.py`, `config_load.py`.

### 1.D `&str` / borrowing (~stretch, may slip to v0.3)

1. Port `depyler-analysis::borrowing` into the xpile workspace as
   `crates/depyler-analysis/`.
2. Add `Type::StrRef { lifetime }` to meta-HIR; introduce
   xpile's first non-trivial lifetime constructs.
3. New contract `contracts/xlate-py-str-borrowing-v1.yaml` — Layer 2,
   captures the borrowing-soundness invariant (no aliased mutation,
   etc.).
4. Diamond theorems for borrowing — first place we cross into
   non-trivial substructural invariants.

1.D is **stretch** because it adds substantive new semantics
(lifetime inference) rather than mechanical port. If 1.A/B/C ship
cleanly and there's capacity left in the v0.2.0 window, take 1.D;
otherwise defer to v0.3.0.

## Exit criterion

```python
# greet.py
def greet(name: str) -> str:
    return f"Hello, {name}!"

def count_chars(name: str) -> dict[str, int]:
    counts: dict[str, int] = {}
    for c in name:
        counts[c] = counts.get(c, 0) + 1
    return counts
```

```bash
$ xpile transpile greet.py
$ xpile transpile greet.py --target ruchy
$ xpile transpile greet.py --target lean
```

— all three produce compileable code carrying
`// xpile-contract: C-XLATE-PY-STR-TO-RUST-STRING` (or analogue)
citations.

`xpile quorum` reports the new contracts at QUORUM. `xpile diamond`
reports the new contracts at depth-1+ minimum.

## Risk register

| Risk | Mitigation |
|---|---|
| Standalone depyler uses a different HIR than xpile-meta-hir; port is non-trivial | Use a "lowering adapter" crate that takes depyler-HIR and emits xpile-meta-hir, rather than touching depyler-HIR. Same approach used for bashrs (`bashrs-frontend` adapts `bashrs::ast` to xpile-meta-hir). |
| Borrowing analysis pulls in `unsafe` or research-grade lifetime inference | Stretch sub-track 1.D is the dumping ground for this. v0.2.0 can ship with owned-only and still claim "real depyler replacement" for most uses. |
| Standalone depyler depends on crates xpile doesn't want to inherit (`depyler-quality`, etc.) | Cull at port time. The "out of scope" table above is the authoritative cull list. |
| Diamond program broadens to 13 new contracts → 30+ new theorems to write | Templates 1, 6, 9, 10, 11, 12, 13 apply mechanically to new contracts. Use the broadening-sweep pattern from PMAT-433..442 (one PR per contract, one PR per template). |

## What this is NOT

- **Not** a clean-room rebuild of Python type lowering. We're porting
  proven, tested standalone code.
- **Not** a depreciation of standalone depyler. The standalone repo
  continues to be the maintenance home for the parser + codegen
  rules; xpile vendors a snapshot, mirrors patches downstream.
- **Not** a one-shot mega-PR. Each sub-track (1.A, 1.B, 1.C) ships as
  its own PR series with QUORUM + Diamond ratchets, same cadence as
  the v0.1.0 substrate work.
